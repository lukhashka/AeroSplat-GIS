# ADR-0006: Project → Site → Epoch → Capture; авторські дані окремо від похідних

**Статус:** запропоновано (2026-10-15); п. 3 змінено [поправкою від 2026-10-15](#поправка-2026-10-15-earth-studio-реконструюється-у-сферичному-enu) · **Див.:** [TARGET_ARCHITECTURE §4, §5, §7](../TARGET_ARCHITECTURE.md), [ARCHITECTURE §4](../ARCHITECTURE.md#4-системи-координат-ключове-для-gis)

## Контекст

Зараз одиниця роботи — «датасет»: одна папка кадрів, один ENU-початок
(середнє координат кадрів), одна сцена. Нові вимоги:

* одну ділянку знімають **з кількох джерел** (Earth Studio, дрон, ручна
  зйомка, інтернет) у різний час;
* для повеней потрібні **стани в часі** («до» і «після»);
* людина розмічає й підтверджує вікна, і перезапуск пайплайна не має цю
  роботу стирати або зсувати.

## Рішення

1. Ієрархія **Project → Site → Epoch → Run**, а **Capture** (партія кадрів
   одного джерела) належить Site і використовується в будь-якій епосі.
2. **Site ENU-початок фіксується при створенні Site** (точка на карті) і
   більше не змінюється. Нові захоплення не зсувають систему координат.
3. Внутрішня модель Землі — **WGS84**: Site ENU, каталог, продукти run-ів і
   `scene-meta` — у WGS84. ~~Адаптер Earth Studio переводить сферичні
   координати в WGS84 на вході й записує похибку переходу у звіт.~~
   *Змінено поправкою:* run Earth Studio реконструюється у сферичному ENU
   ділянки, а сфера → WGS84 застосовується до продуктів.
4. **Run-директорії містять лише похідні дані** і можуть бути видалені й
   перераховані. Авторські дані (підтверджені Feature, цілі, аудит) лежать
   у `sites/<site>/authored/`.
5. Після нового run авторські Feature **переякорюються** similarity-
   трансформацією за спільними кадрами. Якщо залишок більший за поріг,
   Feature переходить у `stale`, а не зсувається мовчки.
6. Каталог зберігається в SQLite (SQLAlchemy/SQLModel + Alembic), великі
   дані — у файлах. На PostgreSQL+PostGIS переходимо, коли з'явиться кілька
   користувачів.

## Альтернативи

* *Лишити «датасет» і додати підпапки* — не розв'язує спільної системи
  координат і стабільності розмітки.
* *Зберігати розмітку в run* — кожен перезапуск втрачає або дублює роботу людини.
* *Одразу PostGIS* — зайва інфраструктура для однієї робочої станції.

## Наслідки

* `RunLayout` стає видом на новий layout; потрібен скрипт міграції `dataset_v6`.
* `DATASET_PATHS` у сервері замінюється читанням каталогу.
* `earthstudio_to_colmap` більше не обирає ENU-початок сам, а отримує його від Site.

## Поправка 2026-10-15: Earth Studio реконструюється у сферичному ENU

### Контекст

Перевірка на `dataset_v6` ([ARCHITECTURE §4](../ARCHITECTURE.md#4-системи-координат-ключове-для-gis))
показала, що рендери Earth Studio узгоджені з його **сферою**, а не з WGS84. Тест такий:
той самий `database.db`, `point_triangulator` із замороженими позами, змінюються лише
центри камер. Сферичні центри дають 0.407 px репроєкції, WGS84-центри — 0.571 px.
Мінімум інтерполяції `wgs84 + k·(сфера − wgs84)` — при k ≈ 1.0. Промені «вперед» камер
Earth Studio сходяться з нев'язкою 0.0000 м лише на сфері. Переведення **поз** у WGS84
на вході (п. 3) робило їх неузгодженими з кадрами на ≈1 м, і BA зсував камери на
1.1–2.5 м (сфера: 0.5 м).

### Рішення

1. Адаптер Earth Studio пише відомі пози у **сферичному ENU** ділянки: центри — з
   `coordinate` як сферичних кутів на радіусі R + altitude (R = 6371008.8 м), origin
   ділянки — з тим самим R. `position` (його радіус має сталі +1.2 м) для поз не
   використовується. Орієнтації не змінюються.
2. Сферичний ENU → WGS84 Site ENU на ділянці майже точно афінне. Для кожного run-а
   адаптер рахує `A, b` методом найменших квадратів на коробці 1×1 км × ±250 м навколо
   origin. Відображення залежить лише від origin, тож однакове для всіх run-ів ділянки.
   На 41° пн. ш. `A ≈ diag(1.002558, 0.998712, 1)`, залишок 0.22 мм (0.85 мм на 2×2 км).
   `A, b` і залишки записуються в `reports/registration.json` і `geo_registration.json`.
3. Нова завершальна стадія `georef` застосовує відображення до продуктів:
   μ → Aμ + b, Σ → AΣAᵀ (масштаби й обертання перераховуються).
   Результат — `gs/*_wgs84.pt`. Саме їх каталог реєструє як `splat`/`cloud` і віддає
   сервер; файли в системі реконструкції лишаються (`splat_recon`/`cloud_recon`) для
   eval і `--resume`.
4. `Run.earth_model = "sphere-enu+affine"` (окремо від `wgs84` — run-и S1 із позами,
   переведеними на вході, — і `sphere-legacy`). `scene-meta.metric.frame_error_m` для
   таких run-ів — залишок афінного відображення.

### Альтернативи

* *Застосовувати `A, b` у сервері (scene-meta)* — суперечить ADR-0001 (сервер лише
  центрує), і кожен наступний споживач продуктів мусив би пам'ятати про відображення.
* *Лишити WGS84 на вході* — систематична ≈1 м неузгодженість поз із кадрами, яку BA
  «лікує» зсувом камер; реконструкція не лежить точно ні в тій, ні в іншій системі.
* *Точне (неафінне) відображення кожного гаусіана* — на ділянці відрізняється від
  афінного менше ніж на 1 мм, а коваріації тоді не переносяться в замкненій формі.

### Наслідки

* Продовжити run з іншим `earth_model` не можна: лише новий run. Стадія `geo` має
  версію у fingerprint, тож `--resume` legacy-run-а перераховує все від `geo`.
* COLMAP-модель run-а (`sfm/`) і `*_recon.pt` — у сферичному ENU. Хто працює з ними
  напряму (майбутнє злиття детекцій, ADR-0008), має застосувати `A, b` зі звіту.
* Абсолютна висота (еліпсоїд чи геоїд EGM96, +1.2 м Google) і далі не перевірена:
  тріангуляція її не бачить, потрібен зовнішній еталон (DEM або контрольні точки).
* Run `sphere-legacy` можна перенести так само: його кадр — сферичний ENU, піднятий на
  1.2 м. Це не зроблено.
